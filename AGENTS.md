# Architecture rules
- Calendar automation date math lives in supabase/functions/_shared/calendarSchedule.ts, re-exported to the UI and selftests, so Berlin-time occurrence keys and previews use the same rules.
- The external scheduler uses a short-lived HMAC signed with the existing server credential; scheduled actions claim calendar slots through the existing unique run index before side effects, so concurrent callbacks cannot duplicate work.
- PDF.js consumers use src/lib/pdfjs.ts, which pairs the installed legacy build with its legacy worker URL; both realms need compatibility APIs such as Uint8Array.toHex, and no consumer may override the shared worker with the modern build or an external URL.
- GDPR deletion approval is generated by the database from the authenticated second administrator; clients send only the request ID, and processors must atomically claim an approved request before destructive work to prevent forged consent and duplicate execution.
- Appointment requests live in their own table and are decided only via the decide_appointment_request RPC (role-checked, creates the appointment atomically); a trigger blocks direct status changes so clients cannot bypass the decider role.
- Case-item triage (ball_owner, next action) logic lives in src/features/cases/items/ball.ts as pure functions; UI and filters import it so rules stay testable in one place.

- Every new business rule or workflow needs a matching step in a selftest scenario (src/features/selftest); pure rules run as kind:"logic" steps so the Selbsttest-Center verifies logic, not just persistence.
- Selftest runs are persisted per tenant in selftest_runs (steps + error details as JSON) so the agent can read failures directly via SQL instead of relying on screenshots.
- Task triage (zones, resubmission, ball handover, timeline events) lives in src/features/tasks/stafette.ts as pure functions; the task workspace UI and selftests import it so rules stay testable.
- After a vote on a task-linked decision, the DB trigger return_task_ball_after_vote hands the task back to the decision's creator (ball_owner office, next step, timeline, notification) so the loop closes without client logic.
- Task nudges go only through the nudge_task/ack_task_nudge RPCs (tenant-checked, 24h limit enforced in DB); due reminders are dispatched hourly by dispatch_due_task_reminders via pg_cron.
- Recurring tasks (tasks.recurrence_rule) are respawned by the DB trigger spawn_recurring_task on completion; mandate templates and recurrence date math live as pure functions in src/features/tasks/templates.ts so they stay testable.
- Appointment briefings move only via set_appointment_briefing/advance_appointment_briefing RPCs (role-checked, create/close the linked task atomically); rules live in src/features/appointments/briefing.ts so UI and selftests share them.
- Jour-fixe system types use a shared registry and bounded tenant-scoped cached loaders across existing views; adding a source must include editor, focus, template and selftest coverage to prevent rendering drift.
- Meeting archival goes through archive_meeting_with_stafette with invoker RLS, a locked meeting and per-meeting source uniqueness; notes document decisions by ID without fabricating votes, while existing voting owns approval and ball return.
- The letter editor's default "page" mode renders the Lexical editor inside LetterEditorCanvas (inlineEditor prop) on one continuous A4 sheet with page-break markers; the split view stays as fallback because a contenteditable cannot be split across separate page DOM nodes.
- Short briefing, 7-phase dossier and live briefing share one preparation_data record via pure converters in src/features/appointments/briefing/briefingModel.ts; live/debrief follow-up tasks go only through create_briefing_follow_up_task so they carry stafette fields and timeline.
- Annual routines are actions in automation_rules, synchronized transactionally to annual_tasks; execute_annual_automation_routine locks the yearly completion before system effects or the shared Stafette processor, so manual and scheduled runs cannot duplicate work and existing completion history survives.
- Automation administration uses one rules/routines/history workspace and RSS monitoring with URL-controlled tabs; legacy annual/engine/RSS links normalize centrally so bookmarks survive while annual actions share the rule executor.
- Calendar leave requests are scoped through tenant profile user IDs and names are joined client-side, because the leave table has neither tenant_id nor a profiles foreign key.
- CommonJS-only packages (e.g. react-big-calendar add-ons) are imported as namespaces and unwrapped via src/lib/cjsInterop.ts, and pre-bundled in optimizeDeps, because Vite can deliver a wrapped default export that crashes at runtime.

- Seasonal office packages use officeRoutineTemplates for editable defaults and execute_annual_automation_routine for atomic parent/subtask creation; yearly date confirmation is checked by both scheduler and database, and annual completion locking prevents duplicate packages.

- Typed office-package steps store routine_step_kinds aligned with routine_steps_text; editor sorting and deletion must update both together. execute_annual_automation_routine creates all targets atomically under the existing yearly completion lock. Jour-fixe steps create pending case items for the existing agenda loader; decisions invite the package assignee without casting a vote.

- Durable routine workflows snapshot steps in routine_package_runs/routine_package_steps. Only automation_private.advance_routine_package creates targets, under a per-run lock and per-step savepoint. Scheduled and dependent steps are advanced every 15 minutes; explicit approvals require the configured person's actual latest yes vote. Template edits affect new runs unless the administrator explicitly applies compatible changes to untouched waiting steps. Never rewrite active targets, cast votes, or re-create a target just because it is missing.

- Rule condition semantics and field types live in supabase/functions/_shared/automationConditions.ts, re-exported through src/features/automation/conditions.ts. Both the browser preview and run-automation-rule use this tree evaluator; the executor takes the module from the stored rule, never from sample data. Date-only targets compare Berlin calendar days; timestamps require an explicit zone. Field-level editor diagnostics originate in ruleValidation.ts and share their paths with inline errors and summary focus links.
- Document annotations live in src/features/annotations and store shapes as 0..1 fractions of page/image size plus a file version stamp, so markings survive zoom and flag outdated files; originals in storage are never modified.

- Annotation follow-up tasks are created only through create_document_annotation_task: it locks the root annotation, validates tenant/assignee membership and atomically writes the Stafette task and unique document_annotation_tasks link. Task links are read-only to clients; deleting an annotation keeps its existing task and document backlink.
- Employee responsibility matching and coverage rules live in src/features/responsibilities/suggest.ts; matrix writes and confirmed task/file assignments use tenant-checked RPCs, while case-item handovers reuse handover_case_items and preserve the existing ball_owner category.

- Employee protocol release/objection/reopening goes only through role-checked RPCs; frozen content is guarded in the database, private notes have per-user storage, and autosave compares a version before writing.

- Employee action tasks are created atomically only after uncontested acknowledgement; both means one task with the employee holding the ball and the supervisor collaborating. Database triggers synchronize completion in both directions.

- Employee review baselines select only the latest earlier completed/acknowledged conversation; open measures keep their original task and review reasons are stored on the current protocol instead of duplicating work.

- Employee preparation opens seven Berlin calendar days before the meeting; the cron dispatcher claims each reminder under a row lock, and optional protocol suggestions fill only empty fields.

- Employee wellbeing JSON and trend RPCs are restricted to the employee and current direct supervisor by database policy, including against older admin ALL policies; thresholds live in the pure wellbeing module and never feed team-wide reports.

- HR onboarding/offboarding reuse routine_package_runs/steps and the existing advance job with immutable employment-date anchors; evidence completion is database-guarded, underlying HR tasks use restrictive privacy policies, and offboarding handovers preserve ball_owner and exclude personal HR targets.

- Annotation history is append-only in document_annotation_events, written by its database trigger under annotation permissions; clients only read it. OCR runs locally with self-hosted worker/core/language assets. Version relocation only proposes a unique text anchor and requires explicit confirmation; export produces a separate PDF copy and never changes originals.

- Responsibility areas may have multiple primary people; UI assignment changes affect only the chosen person, and coverage distinguishes a missing primary contact from a completely unassigned area.

- Topic-to-catalog conversion runs atomically through convert_topic_to_catalog: preserve historical topic links, move employee responsibilities without removing other primaries, and keep topic_catalog_links valid when merging committees or regions.

- Platform election history lives in src/features/election-history and election_history_* tables: only is_superadmin may write, tenants read released periods, candidacies store personal results independently of actual mandate intervals, and succession never counts as re-election. Do not infer person identity from names or overwrite legacy representatives/tenant notes. Load only the selected legislature through get_election_history_period; do not preload other periods or the complete person register. Historical maps draw only the geometry stored for that period; current boundaries are never substituted. Imported member names remain unlinked until a person identity is explicitly confirmed.

- Election mandate date inheritance runs in PostgreSQL before mandate validation and after period date edits; start_from_period/end_from_period distinguish inherited values from individual dates. Never use election day as mandate start or infer succession starts/known early-exit ends. Period preview groups mandates by district_id, independently of candidacy_id.

- Election analysis under Daten uses only election_analysis_* tables and src/features/election-analysis. Result imports never update election_history_* or legacy mandates. The separate superadmin-only apply_verified_election_period RPC may fill missing period dates from verified proposals; preserve existing values and the established mandate date inheritance triggers. Load only the selected year/section/filter; keep first/second votes, preliminary/final results, estimates, missing values, and changing age bands distinct. Do not sum selected parties into full-election totals or double-count turnout across ballot types.

- Historical election comparisons use explicit election_analysis_versions identities backed by verified official geometries; matching names/numbers alone do not establish cross-year identity. Map and table share research/calculations.ts, unknown values stay null, and official result patches compare expected old rows atomically to protect manual edits.
